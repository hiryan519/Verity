# PRD 决策草稿

本文档用于记录正式 PRD 之前的产品决策。当前阶段先记录讨论结论，不写成完整结构化 PRD。

## 产品方向

- 在 Evolva 的 Agent Infra 基础上，补充一个面向 AI 产品经理的 Web 工作台。
- 不从零重建 Evolva 的底层 Agent Runtime。
- Evolva 作为底层能力来源，承载 Loop、Tools、Trace、Eval、Guardrails、Memory、Skills、Workflow 等 Agent Infra 概念。
- Web 产品层负责把底层 Agent 执行过程转译成产品经理可理解、可查看、可确认、可验收的工作流。
- 项目的核心产品决策不能停留在 demo 级别。即使 MVP 代码实现可以分阶段完成，关键机制的设计也必须专业、可解释、可落地。

## 开发路线：复刻式学习与分层实现

### 路线判断

本项目的主要目标是学习和掌握 Agent 产品设计与实现逻辑，而不是追求公开发布或商业上线。

因此，可以采用“复刻式学习”路线：

```text
Verda：学习产品形态、交互体验和竞品研究工作流。
Evolva：作为 Agent Infra 底座和底层能力参考。
InsightFlow：作为开源竞品分析 Agent 的工程与业务流程参考。
本项目：复刻 + 裁剪 + 理解，形成可运行的轻量版本。
```

复刻的重点不是追求原创，而是在复刻过程中回答清楚：

- 这个模块为什么存在？
- 它解决什么 Agent 产品问题？
- 输入和输出是什么？
- 依赖哪些前置数据？
- 它和 Agent 主链路的关系是什么？
- 如果不做会有什么风险？
- 如果简化，最小可行形态是什么？

### 分层复刻范围

第一层：必须复刻，因为它是 Agent 产品核心。

- 专家 Agent 编排。
- 证据采集。
- 证据库。
- 交叉验证 / Analysis Pack。
- 质检 Gate。
- 报告生成。
- 决策链路 Trace。

第二层：尽量复刻，因为它提升产品完整度。

- 报告阅读页。
- 引用定位。
- 图表 + 数据表。
- 我的调研。
- 报告独立 URL。
- 标注 / 加入知识库。

第三层：可以后置，因为它主要是高级体验或工程增强。

- 知识图谱。
- 竞争情报中心。
- 持续追踪。
- 高级编辑。
- 多人协作。
- 复杂舆情分析。
- 自动冲突仲裁。

### 实施策略

开发可以按“先形态、再真实、再机制”的顺序推进：

```text
1. 先用 mock 数据复刻核心页面和交互结构。
2. 再接 Evolva 或 Web Adapter 跑通真实 Agent Workflow。
3. 再逐步让证据库、报告、Trace 从 mock 变为真实数据。
4. 最后补齐置信度、质检、专家选择、返工等关键产品规则。
```

该路线允许阶段性 demo 存在不完整实现，但不允许核心产品机制缺乏明确设计。

## 决策 1：专家库与并行专家组

### 决策

竞品研究工作流需要支持“专家库”和“并行专家分析”机制。

专家库中沉淀多个可复用专家角色，例如：

- 战略咨询专家
- 定价策略专家
- 产品功能分析专家
- 用户声音分析专家
- 技术趋势分析专家
- 市场 / GTM 分析专家
- Reviewer / Synthesizer，负责审查和汇总

针对一次具体研究任务，系统不应默认调用所有专家，而应根据任务目标选择相关专家子集。当多个专家任务之间不存在严格依赖关系时，可以并行分析。

### 产品原因

竞品研究天然是多视角任务。单一 Agent 容易输出线性的、泛化的报告，而产品经理做竞品研究时，通常需要分别从定位、定价、功能、用户、市场、技术等角度形成判断。

并行专家机制适用于：

- 子任务之间互不依赖。
- 各专家可以基于同一任务上下文或共享证据独立分析。
- 各专家输出可以在后续统一合并。
- 相比顺序执行多个 LLM 子任务，并行可以降低整体等待时间。

该机制不应变成“为了多 Agent 而多 Agent”。真正价值在于：让分析视角更清晰、专家输出更结构化，并通过最终审查保证结论质量。

### 执行模型

推荐的工作流形态：

```text
任务定义
  -> 专家选择
  -> 并行专家分析
  -> 汇总 / 冲突识别
  -> 报告生成
  -> 验收报告
```

并行主要用于只读研究和分析任务。依赖前序结论的步骤仍然需要顺序执行。

### Guardrails

- 每个专家必须有明确职责和输出结构。
- 每个专家输出应包含：结论、证据、置信度、风险、待补信息。
- 专家并行阶段不应允许随意写文件、执行 Shell、修改共享状态或调用高风险工具。
- 必须有 Reviewer / Synthesizer 对专家输出做去重、冲突识别、证据校验和最终报告准入判断。
- 如果某个专家失败，系统需要决定是降级继续、重试，还是请求人工介入。

### 与 Evolva 的关系

Evolva 当前已有 role-agent / sub-agent 协作概念，但默认多 Agent 协作和 Workflow 执行更偏顺序执行，并非真正的并行专家分析。

因此，本产品方向可能需要在 Evolva 基础上新增或包装一个能力，暂定名为：

```text
Parallel Expert Group
```

该能力用于并发运行多个只读专家角色，收集结构化专家输出，并交给 Reviewer / Synthesizer 节点统一汇总。

### 待定问题

- 专家选择应该自动完成、由用户手动配置，还是两者都支持？
- MVP 第一版最小专家集合应该包含哪些专家？
- 并行专家执行应该优先改 Evolva 底层，还是先在 Web Adapter 层实现？
- 当某个专家失败或输出低置信度结果时，系统应该如何处理？
- Web 工作台中应该如何展示每个专家的任务、状态、证据和结论？

### 专家角色分配初版

本项目暂不追求“专家越多越好”，而是优先建立少量高价值、职责清晰的专家角色。

MVP 可以先考虑以下角色：

1. Evidence Collector / 资料采集专家
   - 负责搜索、读取和整理竞品相关证据。
   - 输出证据库条目，不直接输出最终结论。
   - 重点关注来源、摘要、相关性、数据缺口。

2. Product Analyst / 产品分析专家
   - 负责功能、定位、核心场景、用户价值和差异点分析。
   - 必须基于证据库形成判断。

3. Business Analyst / 商业与定价分析专家
   - 负责定价模式、套餐策略、商业模式、增长和 GTM 相关分析。
   - 需要区分官方定价信息、第三方解读和推测性判断。

4. User Voice Analyst / 用户反馈分析专家
   - 负责分析可获取的用户评论、社区讨论、issue、评测文章中的用户声音。
   - 不默认承诺能覆盖抖音、小红书等高反爬平台。
   - 当数据不足时，应明确输出数据缺口。

5. Evidence Reviewer / 证据审查专家
   - 负责检查结论是否有足够证据支撑。
   - 识别潜在冲突、证据不足、过度推断和低可信来源。
   - 决定哪些结论可以进入报告，哪些应降级为假设或待验证问题。

6. Report Writer / 报告生成专家
   - 负责将已验证结论组织成结构化竞品分析报告。
   - 不应脱离证据库新增未经验证的核心结论。

后续需要细化：

- 哪些角色必须并行，哪些角色必须顺序执行。
- 每个角色的输入输出 Schema。
- 每个角色可调用的工具范围。
- 自动选专家与人工调整专家之间的交互方式。
- 是否保留“发现层 / 验证层”这样的架构命名，还是在产品界面中使用更直观的“资料采集 / 专项分析 / 证据审查 / 报告生成”。

## 决策 2：数据获取不以“绕过反爬”为产品能力

### 决策

竞品研究需要大量外部信息，但产品不应把“绕过抖音、小红书、微博等平台反爬机制”设计为核心能力。

数据获取策略应优先采用合规、可解释、可降级的方式：

- 官方开放接口或平台授权数据。
- 合规第三方数据服务。
- 搜索引擎可公开检索结果。
- 用户上传或导入的资料。
- 用户手动提供的链接、截图、导出文件或整理后的素材。
- 企业内部已授权的数据源。

如果某个平台无法稳定、合规获取数据，系统应明确标注数据缺口，而不是假装已经完成全量采集。

### 产品原因

竞品研究 Agent 的可信度不只取决于报告写得好不好，还取决于数据来源是否真实、可追踪、可复查。

把“绕过反爬”作为能力会带来几个问题：

- 合规风险高，可能违反平台规则或数据使用边界。
- 稳定性差，平台页面和风控策略变化会导致功能失效。
- 难以复现，报告中的证据链可能不可验证。
- 容易做成演示效果，实际运行时拿不到同样数据。

因此，MVP 应重点展示“证据来源、覆盖范围、可信度和缺口说明”，而不是承诺能抓取所有平台数据。

### 产品设计要求

- 每条证据必须记录来源平台、来源链接或来源文件。
- 每条证据应标注获取方式，例如搜索结果、网页公开内容、用户上传、第三方数据源。
- 对无法访问或证据不足的平台，应在报告和 Validation Report 中明确标注。
- 专家分析时不得把“未获取到的数据”包装成确定结论。
- 系统应支持“证据不足但继续分析”的降级路径，并在最终报告中提示风险。

### 与 Verda 截图的判断

Verda 截图中展示了抖音、小红书、B 站、微博、知乎等平台的口碑采集结果，但目前无法确认这些数据是否真实来自在线抓取，也可能是演示数据或写死内容。

本项目不把这类截图效果作为默认真实能力假设。后续设计时，需要区分：

- Demo 展示数据。
- 公开可访问数据。
- 授权或用户提供数据。
- 不可稳定获取的数据。

### 待定问题

- MVP 是否需要真实接入社媒数据，还是先使用用户上传 / 搜索结果 / 示例数据？
- 如果接入第三方数据服务，优先选择哪些数据源？
- Validation Report 中如何呈现“数据覆盖不足”？
- 证据库是否需要区分高可信来源和低可信来源？

## 决策 3：证据库与证据可信度评分

### 决策

竞品研究工作流需要建设“证据库”。证据库用于集中展示专家在研究过程中采集到的所有证据，并记录每条证据的来源、内容摘要、可信度和使用情况。

证据库中的证据应优先以可复查链接或文件为基础，例如：

- 官方网站页面
- 官方文档
- 定价页
- 新闻报道
- 评测文章
- 用户评论页面
- 社媒链接
- 用户上传资料
- 企业内部授权资料

每条证据需要支持点击打开原始来源。当原始来源不可打开或内容抓取失败时，应明确标注。

### 产品原因

竞品研究报告的可信度不只来自最终结论，还来自结论背后的证据链。

证据库解决几个问题：

- 用户可以复查 Agent 使用了哪些资料。
- 专家分析过程不再是黑盒。
- 最终报告中的关键结论可以回溯到具体来源。
- 数据覆盖不足或证据质量较低时，可以提前暴露风险。
- 后续 Validation Report 可以基于证据质量判断报告是否足够可靠。

### 可信度评分定位

可信度评分不是判断“网页内容绝对真实”，而是判断：

```text
这条证据对当前分析任务是否可靠、相关、可复查、信息充分。
```

因此，可信度更准确地说是“证据质量评分”。

### 评分维度

证据可信度可以由以下维度综合计算：

- 来源类型：官网、官方文档、财报、主流媒体、普通博客、论坛、社媒内容等。
- 可复查性：是否有 URL，是否能打开，是否有标题、时间、作者或平台信息。
- 相关性：内容是否与当前竞品、分析维度和研究目标相关。
- 时效性：内容是否过期，是否近期发布。
- 信息密度：是否包含具体功能、价格、用户反馈、数据、案例，而不是泛泛描述。
- 一致性：是否与其他证据互相支持，是否存在明显冲突。
- 完整性：抓取文本是否过短，是否疑似登录墙、摘要页、广告页、404 或空页面。

### 置信度规则初版

证据置信度不应采用简单的“官网 90 分、评论 50 分”这种粗糙规则，而应拆成多个子分数。

初步公式：

```text
Evidence Confidence
= Source Authority
+ Content Relevance
+ Verifiability
+ Freshness
+ Specificity
+ Cross-source Support
- Risk Penalty
```

初步维度：

- Source Authority / 来源权威性：来源是否官方、权威、可信。
- Content Relevance / 内容相关性：文本是否与当前研究目标、竞品和分析维度相关。
- Verifiability / 可复查性：是否有 URL、标题、发布时间、作者、来源平台等可复查信息。
- Freshness / 时效性：内容是否足够新，是否可能已经过期。
- Specificity / 信息具体性：是否包含具体功能、价格、用户反馈、数据或案例。
- Cross-source Support / 多源支持：是否有其他独立来源支持相同判断。
- Risk Penalty / 风险扣分：是否存在广告软文、转载、内容过短、登录墙、抓取失败、来源不明、过度推断等风险。

后续需要细化：

- 每个子分数的具体分值区间。
- 不同 claim 类型下的证据权重差异。
- 冲突证据如何影响置信度。
- 低置信证据是否允许进入最终报告。
- 哪些置信度阈值会触发 Human Gate。

### 实现原则

MVP 阶段可以采用“规则评分 + LLM 辅助解释”的方式。

规则评分可覆盖：

- URL 是否存在。
- 页面是否成功抓取。
- 来源域名类型。
- 文本长度。
- 发布时间。
- 关键词相关度。

LLM 可用于辅助输出：

- 证据摘要。
- 相关性解释。
- 风险提示。
- 是否适合作为某类结论的支撑证据。

不建议完全依赖 LLM 主观打分，否则容易出现低质量页面被模型误判为高可信证据。

### 推荐数据结构

示例：

```json
{
  "title": "GitHub Copilot Pricing",
  "url": "https://github.com/features/copilot/plans",
  "source_type": "official",
  "platform": "github",
  "captured_at": "2026-07-09",
  "relevance": 92,
  "reliability": 95,
  "freshness": 88,
  "confidence": 91,
  "summary": "官方定价页，适合用于 Copilot 价格和套餐对比。",
  "risk_note": "价格可能随地区或时间变化，需要定期刷新。"
}
```

### 证据与结论绑定

证据库不应只是 URL 列表，还需要记录证据支撑了哪些分析结论。

推荐关系：

```text
结论
  -> 支撑证据 1
  -> 支撑证据 2
  -> 支撑证据 3
```

例如：

```text
结论：Cursor 在 AI coding 体验上更强调上下文理解和项目级协作。
支撑证据：
1. Cursor 官网功能页，可信度 92。
2. 用户评论整理，可信度 66。
3. 技术博客评测，可信度 74。
```

### 待定问题

- MVP 第一版是否需要真实网页抓取，还是先支持用户输入 URL 并做基础解析？
- 证据可信度分数是否展示为 0-100，还是高 / 中 / 低等级？
- 报告中的每个关键结论是否强制绑定至少一条证据？
- 低可信证据是否允许进入最终报告？
- 证据库是否需要支持按专家、平台、来源类型、可信度筛选？

## 决策 4：交叉验证与报告前质检策略

### 决策

竞品研究报告不应在证据采集后直接生成。系统需要先把证据加工成结构化的中间分析资产，再通过报告前质检判断是否可以进入最终报告撰写。

推荐流程：

```text
证据采集
  -> 交叉验证 / 结构化分析
  -> 报告前质检
  -> 通过则生成完整报告
  -> 不通过则返工补充
```

报告前质检不是检查最终报告，而是检查“报告素材包”是否足以支撑一份可靠的竞品分析报告。

### 交叉验证产物

交叉验证阶段的产物可以暂定为 Research Brief / Analysis Pack。

它应包含：

- 竞品知识 Schema：每个竞品的定位、目标用户、核心功能、定价模式、优势、劣势、用户反馈、风险等字段。
- 结构化论点：从证据中提炼出的可审查判断。
- 证据绑定：每个关键判断需要关联对应证据。
- 置信度：每个判断需要给出初步置信度。
- 数据缺口：哪些平台、维度或竞品证据不足。
- 潜在冲突：不同来源之间存在矛盾或口径不一致的地方。

交叉验证的目标不是写完整报告，而是形成“可写报告的结构化素材包”。

### 质检员职责

质检员负责检查 Research Brief / Analysis Pack 是否达到进入报告生成的质量门槛。

重点检查：

- 证据覆盖是否足够。
- 来源是否过于单一。
- 关键竞品是否都有覆盖。
- 核心分析维度是否都有证据支撑。
- 关键结论是否绑定证据。
- 是否存在未处理的冲突。
- 是否存在低置信证据支撑强结论。
- 是否存在明显数据缺口。
- 是否有过度推断或脱离证据的判断。

### 质检评分维度初版

质检员可以采用 0-100 分制，并输出 pass / rework。

初步评分维度：

- 证据充分性：证据数量、覆盖范围和关键字段支撑是否足够。
- 维度完整性：功能、定位、定价、用户反馈、市场等核心维度是否完整。
- 结论可信度：核心判断是否由足够可靠的证据支持。
- 结构化完整度：Research Brief / Analysis Pack 是否结构清晰、字段完整。
- 证据一致性：是否存在未解释的冲突、口径差异或明显矛盾。
- 数据缺口风险：缺失数据是否影响最终报告可信度。

示例输出：

```json
{
  "verdict": "rework",
  "scores": {
    "evidence_sufficiency": 42,
    "dimension_completeness": 85,
    "claim_reliability": 38,
    "structured_completeness": 92,
    "evidence_consistency": 75,
    "data_gap_risk": 60
  },
  "issues": [
    "用户反馈证据不足，当前结论主要来自二手评测文章。",
    "定价信息缺少官方来源支撑。"
  ],
  "recommendations": [
    "补充每个竞品的官方定价页。",
    "将用户口碑相关结论降级为初步观察。"
  ],
  "next_action": "补充证据后重新质检"
}
```

### 返工策略

系统需要支持质检不通过后的返工，但不能无限返工，避免 Agent 陷入循环。

MVP 阶段参考 Verda 的策略：

```text
最多返工 1 次。
```

返工方向应由质检员给出明确建议，例如：

- 补充某个竞品的官方资料。
- 补充某个维度的证据。
- 降级某个证据不足的结论。
- 删除无法被证据支撑的判断。
- 标注数据缺口并继续生成报告。

如果返工后仍未通过，系统应允许生成“带风险提示的报告”，或者要求用户人工确认是否继续。

### 待定问题

- 质检通过阈值应该是多少？
- 哪些维度必须达标，哪些维度可以带风险通过？
- 返工后仍不通过时，默认策略是终止、人工确认，还是生成带风险报告？
- 质检员是否应该由固定 Reviewer 执行，还是由专门的 QA Agent 执行？
- 质检分数是否进入最终 Validation Report？

## 决策 5：报告阅读与结构化分析资产展示

### 决策

最终报告不应只是单篇长文，而应是一个可交互、可追溯、可复用的研究档案。

报告结构不在当前阶段固定死。系统应支持模块化报告，根据任务目标、竞品类型和可用证据动态选择分析模块。

可选模块包括：

- 竞争格局
- 功能矩阵
- 商业模式 / 定价
- 目标用户 / 场景画像
- 发展轨迹 / 趋势
- SWOT
- 用户反馈 / 公开反馈
- 风险与不确定性
- 证据图集

### 产品原则

报告展示层的核心不是“排版好看”，而是让 Agent 产出的分析结论可验证、可追溯、可二次使用。

因此，报告页面应同时承载：

- 正文分析。
- 图表。
- 图表对应的数据表。
- 信源引用。
- 证据库。
- 可导出的结构化数据。

### 图表与数据表

图表不能只是装饰，应来自前序 Analysis Pack 中的结构化数据。

设计原则：

- 每个图表都应有对应数据表。
- 数据表应展示数据名、值、指标、来源、来源网址或来源说明。
- 图表数据应支持导出 CSV，方便用户放入 PPT、周报、PRD 或其他汇报材料。
- 图表数据需要区分来源类型：
  - 官方数据。
  - 第三方数据。
  - 用户反馈统计。
  - 模型归纳。
  - 分析推断。
  - 用户输入。
- 推断型数据必须显式标注，不能伪装成事实数据。

### 功能矩阵与能力图表

功能矩阵类章节可采用：

```text
能力雷达图
  -> 数据表
  -> 功能树
  -> 证据引用
```

能力雷达图用于快速比较竞品在关键维度上的强弱。

功能树用于解释每个竞品具体有哪些功能点、能力标签和产品结构。

能力评分和功能标签都应来自结构化分析数据，并尽量绑定证据来源。

### 定价与商业模式图表

价格对比适合图表化，但必须注意价格口径。

数据表中应尽量记录：

- 价格数值。
- 计费周期。
- 套餐名称。
- 目标用户。
- 包含额度或权益。
- 来源链接。
- 备注说明。

当不同竞品价格口径不一致时，应在报告中说明，不应直接进行强对比。

### 用户反馈 / 公开反馈模块

不建议默认使用“全网舆情”作为模块名称，除非确实具备稳定、合规、覆盖充分的数据来源。

更稳妥的命名是：

```text
用户反馈 / 公开反馈
```

可用来源包括：

- 公开网页。
- 搜索结果摘要。
- GitHub issues / discussions。
- Product Hunt。
- Reddit / Hacker News。
- 知乎公开内容。
- B 站公开内容。
- 用户上传截图或整理材料。
- 合规第三方数据服务。

对于抖音、小红书、微博等不稳定或难以合规采集的平台，应明确标注是否覆盖，不能默认宣称已完成全网采集。

用户反馈统计应设置样本门槛：

- 样本量不足时，只展示原声摘录，不展示比例统计。
- 样本量达到一定规模后，才展示情感分布或平台分布。
- 平台口碑分布必须展示样本来源和样本数量。

### 证据图集

除结构化证据库外，可以增加“证据图集”模块，用于展示采集到的网页或媒体页面卡片。

证据图集的作用是增强可复查感：

- 展示网页标题。
- 展示来源域名。
- 展示预览图或 favicon。
- 展示摘要。
- 标注关联竞品。
- 点击可打开原始页面。

MVP 可先做链接卡片，不必立即实现完整网页截图采集。

### 待定问题

- 第一版报告需要支持哪些最小模块？
- 图表数据表是否作为 P0 功能实现？
- CSV 导出是否进入 MVP？
- 推断型数据的标注样式如何设计？
- 用户反馈统计的样本量门槛具体是多少？
- 证据图集第一版采用网页预览卡片还是截图卡片？

## 决策 6：决策链路 / Agent Trace 回放

### 决策

报告页面需要提供“决策链路”入口，用户可以从最终报告跳转到 Agent 执行过程页，查看整份报告从任务理解、专家派发、证据采集、交叉分析、质检审查到报告撰写的完整过程。

决策链路不是普通日志，而是面向产品用户的 Agent Trace 回放。

它用于回答：

- Agent 做了哪些步骤？
- 每一步由哪个专家或工具完成？
- 每一步使用了什么模型？
- 每一步输入、Prompt、输出是什么？
- 每一步消耗了多少 Token 和时间？
- 最终报告中的结论可以追溯到哪些中间步骤？

### 产品原因

Agent 生成的报告如果只展示最终结果，会形成黑盒。决策链路用于增强过程透明度、可审计性和可复盘性。

它主要解决：

- 追溯：用户可以回看报告是如何生成的。
- 调试：当结论错误时，可以定位是证据、Prompt、专家分析还是报告撰写阶段的问题。
- 成本治理：查看总 Token、总耗时、每个阶段和每个专家的消耗。
- 质量复盘：质检、返工、低置信结论等过程可以被完整记录。
- 用户信任：用户不只看到结果，还能看到关键决策链路。

### 页面结构

决策链路页面建议包含三层：

1. 总览层
   - 总 Token 消耗。
   - 总耗时。
   - 总步骤数。
   - 涉及专家数。
   - 是否发生返工。

2. 阶段筛选层
   - 全部。
   - 需求理解。
   - 编排派遣。
   - 证据采集。
   - 交叉分析。
   - 报告撰写。
   - 质检审查。
   - 签发交付。

3. 单步详情层
   - Agent / 专家名称。
   - 任务名称。
   - 模型名称。
   - Token 输入、输出、总量。
   - 耗时。
   - 状态。
   - Prompt。
   - 输入。
   - 输出。
   - 关联证据。
   - 关联报告章节。

### 推荐数据结构

示例：

```json
{
  "step_id": "step_105",
  "stage": "report_writing",
  "agent": "Report Writer",
  "task": "撰写章节：结论与行动建议",
  "model": "primary_model",
  "input": "...",
  "prompt": "...",
  "output": "...",
  "token_input": 4798,
  "token_output": 1261,
  "token_total": 6059,
  "duration_seconds": 38.7,
  "status": "success",
  "related_evidence_ids": ["ev_001", "ev_024"],
  "related_report_sections": ["section_13"]
}
```

### 与 Evolva 的关系

Evolva 已有 Trace 能力，后续可以将底层 Trace event 转换为 Web 端可读的 Decision Trace。

转换方向：

```text
Evolva 底层 Trace
  -> PM 可读的决策链路
```

底层事件如 tool_call、llm_response、context_write 等，需要映射到产品阶段，如证据采集、专家分析、质检、报告撰写。

### 隐私与安全边界

展示 Prompt / Input / Output 时需要考虑安全和隐私：

- API Key、密钥、Cookie 等敏感信息必须脱敏。
- 用户隐私数据需要隐藏或折叠。
- 超长 Prompt 和输出默认折叠。
- MVP 阶段先支持只读查看，不支持编辑。
- 是否允许复制、导出或分享，需要后续再定。

### 待定问题

- 决策链路是否作为 MVP 的 P0 功能？
- Evolva Trace event 到 Web Decision Trace 的字段映射如何设计？
- 是否需要记录成本金额，还是只记录 Token 和耗时？
- Prompt / Input / Output 默认展示到什么粒度？
- Trace 与报告正文、证据库之间如何双向跳转？

## 决策 7：报告生命周期管理

### 决策

产品不应只支持“生成一份报告”，还应支持报告生成后的管理、编辑、分享、沉淀和复查。

报告应被视为可持续使用的研究资产，而不是一次性 AI 输出。

初步包含：

- 我的调研。
- 报告独立 URL。
- 报告编辑模式。
- 知识图谱。

### 我的调研

“我的调研”是历史调研报告管理页，用于集中管理用户已完成或进行中的竞品研究。

每张调研卡片应展示：

- 报告标题。
- 分析对象。
- 生成时间。
- 证据数量。
- 独立信源数量。
- 高置信结论数量。
- 是否发生返工。
- 入口：打开报告、查看知识图谱、继续编辑或复查。

该模块属于产品基础信息架构，优先级较高。

### 报告独立 URL

每份报告应有独立 URL，便于用户分享、复查和后续继续编辑。

报告独立 URL 的目标是让调研报告更像一个可流转的文档资产，而不是一次性生成结果。

权限和分享范围后续再细化，MVP 可先支持本地或单用户可访问。

### 报告编辑模式

报告需要支持编辑模式。用户可以点击正文段落，将该段落切换为编辑状态，直接新增、修改或删除文字。

编辑能力解决的是：

- Agent 生成后，用户需要人工润色。
- 用户需要修正口径或补充业务判断。
- 用户不希望复制到外部文档后再改。

编辑模式需要注意证据链一致性问题。用户修改正文后，原有证据引用和结论状态可能失效。

因此，编辑行为至少应记录：

- 编辑人。
- 编辑时间。
- 编辑段落。
- 编辑前内容。
- 编辑后内容。
- 是否影响引用。
- 是否标记为 user-edited。

MVP 可以先支持：

- 段落级编辑。
- 保存 / 取消。
- 编辑历史记录。
- 标记 user-edited。

后续再考虑：

- 编辑后引用校验。
- 编辑后重新质检。
- 版本对比。
- 多人协作评论。

### 知识图谱

知识图谱用于可视化报告、结论和证据之间的关系。

基础结构：

```text
报告节点
  -> 结论节点
  -> 证据节点
```

它用于展示：

- 一份报告包含哪些核心结论。
- 每个结论由哪些证据支撑。
- 同一证据是否支撑多个结论。
- 哪些结论证据薄弱。
- 哪些证据是高频核心信源。

知识图谱的前提是系统已经建立 claim-evidence 绑定关系。如果没有结构化关系数据，图谱容易变成装饰性功能。

MVP 可先做最小三层图谱：

- 报告：中心节点。
- 结论：围绕报告的节点。
- 证据：围绕结论的节点。

基础交互：

- 拖拽。
- 缩放。
- 点击节点查看详情。
- 点击证据打开原始链接。
- 点击结论跳转到报告段落。

后续增强：

- 节点大小表示引用次数。
- 边粗细表示支撑强度。
- 颜色深浅表示置信度。
- 支持按竞品、章节、置信度筛选。

### 优先级初版

```text
P0：我的调研
P0：报告独立 URL / 可分享
P1：报告段落编辑
P1：最小知识图谱
P2：编辑后重新质检
P2：高级知识图谱交互
```

### 待定问题

- 我的调研是否需要支持草稿、运行中、已完成等状态？
- 报告分享是否需要权限控制？
- 编辑后是否必须触发引用校验？
- claim-evidence 绑定是否进入 MVP？
- 知识图谱是否作为 MVP 展示亮点，还是后置到 P1？

## 决策 8：专家库作为 Expert Agent Library

### 决策

专家库不应被理解为静态 Skill 列表，也不需要做成几十个长期在线的人格化 Agent。更合理的产品抽象是任务型 Expert Agent：

```text
Expert Agent = Role + Goal + Tool Scope + State + Output Schema + Trace
```

也就是说，专家需要具备独立任务目标、状态、工具边界、输出结构和 Trace。Skill 不再作为专家本体，而是专家 Agent 可调用的方法、知识、Prompt 片段或工具规范。

每个专家包含：

- 角色定位。
- 任务目标。
- 适用任务。
- 系统 Prompt。
- 擅长分析维度。
- 可用工具范围。
- 运行状态。
- 输出 Schema。
- 质量要求。
- Trace 字段。
- 所属层级。

任务执行时，系统根据研究目标选择合适的 Expert Agents，并由主控 workflow 调度它们执行顺序或并行任务。

### 产品原因

这种设计相比“角色 Prompt + Skill 调用”更能体现多 Agent 编排，也比长期人格化 Agent 更可控：

- 保留独立 Agent 的任务状态、并行执行和 Trace。
- 专家职责更清晰。
- 输出格式更稳定。
- 便于复用和维护。
- 便于和 Evolva 的 Skills 能力衔接。

多 Agent 协作在本项目中体现为：

```text
主控编排器
  + 专家 Agent
  + 工作流状态
  + 共享证据库
  + 结构化输出
  + 质检与返工机制
```

### 专家分层

专家库可以按职责分层展示。参考 Verda 的思路，初步采用：

- 决策层：负责最终判断、质检、报告签发和风险裁决。
- 策略层：负责战略分析、定价、定位、用户画像、产品判断。
- 执行层：负责资料采集、数据分析、图表生成、证据整理。

该分层比“发现层 / 验证层”更适合作为用户可见的专家库分类。

### MVP 范围

MVP 不追求完整专家数量，可以先建设 6-8 个核心 Expert Agents。

优先保留：

- Evidence Collector / 资料采集专家。
- Product Analyst / 产品分析专家。
- Business Analyst / 商业与定价分析专家。
- User Voice Analyst / 用户反馈分析专家。
- Evidence Reviewer / 证据审查专家。
- Report Writer / 报告生成专家。

### 优先级初版

```text
P0：最小专家 Agent Library
P0：专家分类与详情
P1：专家贡献统计
P2：专家贡献榜
P2：专家 Agent 的用户自定义配置
```

### 待定问题

- 专家 Agent 配置文件应如何存储？
- 专家是否允许用户自定义？
- 专家与 Evolva Skills 如何映射？
- 专家可用工具范围如何配置？
- 专家贡献如何统计：任务数、结论数、证据数、报告引用次数，还是综合评分？

## 决策 9：竞争情报中心

### 决策

产品需要一个跨报告的“竞争情报中心”，用于沉淀和统计所有调研产生的结构化资产。

竞争情报中心不是单份报告的一部分，而是跨报告、跨竞品、跨时间的情报资产看板。

它用于把一次次调研沉淀为长期可运营的竞争情报资产。

### 产品价值

竞争情报中心解决的问题：

- 用户可以看到已覆盖多少竞品。
- 用户可以看到累计沉淀了多少证据、结论和信源。
- 用户可以评估调研质量，例如交叉验证率、高置信结论占比。
- 用户可以按竞品、来源、专家、报告追溯情报资产。
- 后续可以从一次性竞品分析升级为持续竞争情报监控。

### 核心指标初版

竞争情报中心可展示：

- 覆盖竞品数。
- 情报证据数。
- 产出结论数。
- 交叉验证率。
- 独立信源数量。
- 高置信结论数量。
- 累计 Token 消耗。
- 累计耗时。
- 调研报告数。
- 专家贡献统计。

### 模块初版

1. 总览指标
   - 覆盖竞品。
   - 情报证据。
   - 产品结论。
   - 交叉验证率。

2. 每次调研概览
   - 报告卡片。
   - 竞品标签。
   - 证据数。
   - 结论数。
   - 高置信数量。
   - 效率提升或耗时指标。
   - 报告入口。
   - 决策日志入口。

3. 竞品情报图谱 / 情报厚度
   - 按竞品统计证据数量、信源类型、平均可信度。
   - 用于判断哪些竞品研究较充分，哪些仍是认知盲区。

4. 信源结构分析
   - 官方来源。
   - 媒体报道。
   - 社媒 / 社区反馈。
   - 用户上传。
   - 第三方数据。

5. 全局证据库
   - 跨报告检索所有证据。
   - 按竞品、来源、可信度、报告筛选。

6. 专家贡献统计
   - 统计每个 Expert Agent 参与了多少任务。
   - 贡献了多少结论、证据或章节。

7. 竞品持续追踪
   - 允许用户订阅竞品关键词或对象。
   - 后续可定期刷新动态、发现变化并生成增量提醒。

### 优先级初版

```text
P1：轻量情报中心
P1：每次调研概览
P1：专家贡献统计
P2：全局证据库统计
P2：信源结构分析
P2：竞品持续追踪
P2：情报厚度排名
```

### 实现边界

竞争情报中心依赖底层结构化数据。如果没有真实的报告、证据、结论、信源、专家执行记录，情报中心容易变成静态仪表盘。

因此 MVP 阶段可以先做轻量版，优先展示已有报告和证据统计，不急于实现完整持续追踪和高级情报分析。

### 待定问题

- 竞争情报中心是否进入 MVP，还是作为 P1？
- 哪些指标是真实统计，哪些是估算指标？
- “效率提升 / 省人力”如何计算，是否需要避免夸大？
- 竞品持续追踪是否需要定时任务和通知系统？
- 全局证据库是否与用户个人知识库合并，还是保持独立？

## 决策 10：Research Memory Layer 记忆系统

### 决策

本项目需要重点设计记忆系统，但不应把“历史报告、知识库、证据库”简单等同于 Agent Memory。

知识库和历史报告更偏资产存储；真正的 Agent Memory 必须满足：

```text
它会影响下一次 Agent 如何理解任务、选择专家、采集证据、生成报告、判断风险或调整输出风格。
```

因此，后续开发前需要专门针对记忆系统进行产品决策设计，不能只停留在“把内容存起来”。

### 与 Evolva 的关系

Evolva 已有轻量记忆系统，包含：

- kind：记忆类型。
- content：记忆内容。
- confidence：置信度。
- source：来源。
- evidence：证据。
- status：状态，例如 active / draft / quarantined / rolled_back。
- version：版本。
- supersedes：替代关系。

Evolva 的记忆系统适合作为本项目 Research Memory 的治理基础，但原生能力偏轻量，不应直接等同于完整业务记忆系统。

本项目应在 Evolva Memory 之上设计一层竞品研究场景的 Research Memory Schema。

### 记忆类型初版

Research Memory 可以先分为以下类型：

1. user_preference / 用户偏好记忆
   - 用户常关注的分析维度。
   - 用户偏好的报告风格。
   - 用户常用输出格式。
   - 用户常分析的行业或竞品。

2. research_pattern / 调研方法记忆
   - 某类产品的常用分析框架。
   - 某类行业的重点关注维度。
   - 有效的专家组合和工作流模式。
   - 质检 checklist 或常见风险项。

3. competitor_fact / 竞品事实记忆
   - 已验证的竞品功能、定价、定位、用户群体等事实。
   - 必须绑定证据、时间和来源。

4. validated_insight / 已验证洞察
   - 通过质检的高置信结论。
   - 可在后续报告中作为历史洞察或背景补充。

5. expert_lesson / 专家经验
   - 某个专家 Agent 在任务中沉淀出的改进建议。
   - 可用于优化专家 Prompt、工具选择或输出 Schema。

6. report_style / 报告风格记忆
   - 用户对报告表达、结构、详略程度的偏好。

### 写入规则初版

不是所有内容都可以自动进入记忆。

可以写入的候选：

- 用户明确要求记住。
- 用户标注为“认同”或“亮点”的片段。
- 通过质检的高置信结论。
- 多次调研重复出现的稳定模式。
- 用户手动确认的偏好。
- 返工或质检中沉淀出的专家经验。

不应自动写入：

- 低置信结论。
- 冲突未解决的判断。
- 单一来源支撑的强推断。
- 临时任务上下文。
- 未经确认的用户偏好。
- 敏感信息。
- 明显过期或不可复查的信息。

### 召回使用规则初版

不同记忆类型应影响不同环节：

- user_preference：影响报告风格、模块选择、输出格式。
- research_pattern：影响任务拆解、专家选择、质检标准。
- competitor_fact：影响增量调研、历史对比、背景补全。
- validated_insight：影响执行摘要、趋势分析、历史结论对比。
- expert_lesson：影响专家 Agent 的 Prompt、工具选择和执行策略。
- report_style：影响 Report Writer 的写作方式。

如果一条记忆不会影响后续执行，它更像知识库资产，而不是真正的 Agent Memory。

### 记忆治理

记忆系统必须有治理机制，避免错误记忆污染 Agent 行为。

需要设计：

- 置信度。
- 来源。
- 证据。
- 状态：active / draft / quarantined / deprecated / rolled_back。
- 时间戳。
- 过期策略。
- 用户可查看、编辑、删除。
- 冲突处理。
- 审计日志。

低置信、冲突、缺少证据的内容应进入 draft 或 quarantined，而不是直接进入 active memory。

### 与知识库 / Skill 的边界

需要区分：

```text
知识库：用户收藏、沉淀和检索的内容资产。
Memory：会影响下一次 Agent 行为的长期记忆。
Skill：可复用的方法、流程、Prompt、专家能力或 checklist。
```

加入知识库不等于自动写入 Memory；写入 Memory 也不等于沉淀为 Skill。

### 与 mem0 的关系

mem0 这类通用记忆系统适合处理用户长期偏好、跨会话个人记忆和语义召回。

但竞品研究中的证据、报告、claim-evidence 关系、质检结果和图表数据更适合由业务数据库或 Research Memory Schema 管理。

后续可以采用混合架构：

```text
业务数据库：证据、报告、claim-evidence、图表数据。
Evolva Memory：治理型 lesson / research memory。
Evolva Skill：专家 Agent 可调用的方法型知识、Prompt 片段和工具规范。
mem0：用户长期偏好和跨会话个人记忆，可选。
```

### 后续必须重点细化的问题

开发 TODO 前必须进一步细化：

- MVP 是否真正实现 Research Memory，还是先设计数据结构。
- 哪些记忆类型进入 MVP。
- 每类记忆的写入触发条件。
- 每类记忆的召回时机。
- 记忆如何影响专家选择和报告生成。
- 记忆是否需要人工确认后才能 active。
- 记忆污染如何发现和回滚。
- 记忆是否进入最终 Validation Report。
- 是否需要接入 mem0，还是先基于 Evolva Memory 扩展。

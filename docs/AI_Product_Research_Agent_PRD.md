# AI Product Research Agent Console PRD

版本：v0.1  
状态：开发前结构化 PRD 草案  
基础参考：Evolva Agent Infra、Verda 产品形态、InsightFlow 竞品分析 workflow、现有 PRD 决策草稿

## 1. 产品定位

AI Product Research Agent Console 是一个基于 Evolva Agent Infra 的产品经理竞品研究工作台。

它不是单纯的“竞品分析报告生成器”，而是将竞品研究拆解为可编排、可追踪、可质检、可沉淀的 Agent Workflow：

```text
研究目标输入
  -> 专家 Agent 编排
  -> 证据采集
  -> 证据库与可信度评分
  -> 交叉验证 / Analysis Pack
  -> 质检 Gate
  -> 报告生成
  -> 引用追溯 / 决策链路 / 知识沉淀
```

产品目标是帮助 AI 产品经理、产品经理和策略/增长岗位，将高频竞品调研工作从“一次性报告生成”升级为“证据驱动的研究资产生产流程”。

### 1.1 与 Evolva 的关系

Evolva 作为底层 Agent Infra，提供或启发以下能力：

- Loop / Workflow：任务分阶段执行。
- Tools：搜索、读取网页、文件处理等工具调用。
- Trace：记录执行过程。
- Eval / Gate：评估和质量控制思路。
- Memory / Skills：记忆治理、专家可调用能力和方法沉淀基础。
- Guardrails：工具调用边界、风险控制和人类确认。

本产品在 Evolva 之上补充 Web 产品层：

- 面向 PM 的任务流可视化。
- 专家 Agent 编排。
- 证据库与可信度。
- 可追溯报告阅读体验。
- 决策链路回放。
- 调研资产管理。

## 2. 用户

### 2.1 核心用户

1. AI 产品经理
   - 需要快速理解竞品、行业机会和产品差异。
   - 关注 Agent 是否能把复杂调研流程做得可控、可信、可复盘。

2. 产品经理
   - 需要做竞品分析、PRD 背景调研、功能矩阵、用户画像、商业模式对比。
   - 希望调研结果可引用、可导出、可分享、可沉淀。

3. 策略 / 增长 / 市场研究人员
   - 关注竞品动态、定价、市场定位、用户反馈、增长动作。
   - 需要跨报告汇总和持续追踪能力。

### 2.2 MVP 目标用户

MVP 优先服务单用户、本地使用场景：

- 用户在本地输入研究目标和竞品对象。
- 系统生成一份带证据、质检和 Trace 的竞品分析报告。
- 用户能查看证据、报告、决策链路和历史调研。

暂不优先支持团队协作、权限体系、多租户和企业级数据源接入。

## 3. 用户痛点

### 3.1 传统竞品分析痛点

- 资料来源分散，搜索、摘录、整理耗时。
- 报告结论依赖个人判断，证据链不清晰。
- 数据口径不统一，价格、用户反馈、市场数据容易误读。
- 报告写完后难以复用，历史调研资产沉淀弱。
- 图表和数据难以导出到 PPT、周报或 PRD。

### 3.2 普通 AI 报告生成器痛点

- 一次性生成长文，过程黑盒。
- 不知道用了哪些资料，也不知道资料是否可靠。
- 缺少证据可信度和数据缺口说明。
- 缺少报告前质检，容易把弱证据写成强结论。
- 缺少 Trace，无法定位错误来自采集、分析、Prompt 还是撰写。
- 缺少记忆和沉淀机制，下次调研仍从零开始。

### 3.3 Agent 产品风险

- 多 Agent 容易变成角色 Prompt 堆叠。
- 社媒数据采集容易被夸大，反爬和合规风险高。
- 图表如果没有数据表支撑，会变成“AI 幻觉图表”。
- 记忆如果缺少写入和治理规则，会污染后续分析。
- 质检和返工如果没有边界，可能造成死循环。

## 4. 产品目标

### 4.1 MVP 目标

在本地实现一个可运行的轻量版本，打通竞品研究 Agent Workflow 的核心链路：

- 用户输入调研目标和竞品对象。
- 系统选择或展示专家 Agent。
- 系统采集或模拟采集证据。
- 系统生成证据库和证据可信度。
- 系统生成 Analysis Pack。
- 系统执行报告前质检。
- 系统生成带引用和图表的报告。
- 用户可以查看决策链路 Trace。
- 用户可以在“我的调研”查看历史报告。

### 4.2 学习目标

通过该项目掌握 AI PM 视角下 Agent 产品的核心能力：

- 任务拆解与专家 Agent 编排。
- 工具调用和数据源边界。
- 证据链、可信度和数据缺口。
- 质检 Gate、返工和 Human-in-the-loop。
- Trace 回放和成本治理。
- 报告产物、知识沉淀和记忆系统边界。

## 5. MVP 范围

### 5.1 P0 必须实现

1. 研究任务创建
   - 输入研究目标。
   - 首页只保留一句话自然语言输入，不在首页展开复杂配置。

2. 调研范围确认
   - Agent 识别产品/领域并让用户确认。
   - 用户配置候选竞品、分析维度、报告视角、目标市场、目标用户、时间范围和补充说明。
   - 确认后再进入调研执行。

3. 最小专家 Agent Library
   - 资料采集专家。
   - 产品分析专家。
   - 商业与定价分析专家。
   - 用户反馈分析专家。
   - 证据审查专家。
   - 报告生成专家。

4. 证据库
   - 展示证据标题、URL、来源类型、摘要、可信度。
   - 支持点击打开原始来源。
   - 支持按来源类型和可信度查看。

5. 证据可信度初版
   - 使用多维度规则框架。
   - 至少展示总分、来源类型、风险提示。

6. Analysis Pack
   - 生成结构化竞品知识 Schema。
   - 包含核心论点、证据引用、置信度、数据缺口。

7. 质检 Gate
   - 对 Analysis Pack 做维度评分。
   - 输出 pass / rework。
   - 最多返工 1 次。

8. 报告阅读页
   - 左侧目录。
   - 中间正文。
   - 右侧证据库。
   - 章节结论带信源引用。

9. 决策链路 Trace
   - 展示总 Token、总耗时、步骤数。
   - 按阶段筛选。
   - 单步可展开 Prompt / Input / Output。

10. 我的调研
   - 展示历史报告卡片。
   - 支持打开报告。
   - 每份报告有独立 URL。

### 5.2 P1 尽量实现

- 图表 + 数据表。
- CSV 导出。
- 报告标注、批注、加入知识库。
- 报告段落编辑。
- 最小知识图谱。
- 轻量竞争情报中心。
- 专家贡献统计。
- Research Memory 数据结构和部分写入规则。

### 5.3 P2 后续增强

- 竞品持续追踪。
- 高级知识图谱交互。
- 编辑后重新质检。
- 自动冲突仲裁。
- 复杂用户反馈/舆情分析。
- mem0 或其他长期记忆系统接入。
- 多人协作和权限控制。

### 5.4 明确不做

MVP 不承诺：

- 绕过抖音、小红书、微博等平台反爬。
- 完整全网舆情采集。
- 生产级多用户权限。
- 生产级定时追踪和通知。
- 完整 claim-level 自动事实核验。
- 企业级部署、安全审计和合规体系。

## 6. 信息架构与页面 UI/UX 说明

本节作为页面设计输入，不只罗列页面，还定义全局导航、页面层级、布局结构、关键交互和页面跳转关系。

### 6.1 全局信息架构

产品采用左侧主导航 + 中央工作区的应用式布局。

左侧主菜单包含 5 个一级入口：

```text
1. 工作台
2. 我的调研
3. 知识库
4. 专家公会
5. 竞争情报中心
```

详情类页面不一定出现在左侧主菜单中，但可以从主菜单页面跳转进入：

```text
调研执行页
报告阅读页
决策链路页
知识图谱页
报告编辑模式
```

全局布局建议：

- 左侧导航宽度固定，展示产品名、一级菜单、工作空间信息。
- 中央区域承载当前页面主内容。
- 需要阅读和证据联动的页面采用三栏布局。
- 需要可视化图谱的页面采用全屏画布布局。

### 6.2 一级菜单 1：工作台

#### 6.2.1 页面：工作台首页 / 新建调研

用途：创建新的竞品研究任务，是用户进入核心 workflow 的起点。

布局：

```text
左侧：全局导航
中间：欢迎语 + 大输入框 + 示例任务
底部或侧边：专家头像 / 工作空间摘要
```

中间主区域包含：

- 欢迎语：例如“下午好，林研究员”。
- 产品说明：一句话说明这是 AI 竞品研究 Agent。
- 大输入框：支持自然语言描述调研目标。
- 提交按钮。
- 示例任务卡片：新能源车竞争格局、竞品 SWOT 分析、功能对标基准、市场趋势报告等。
- 可选展示专家头像或专家数量，增强“专家协作”感。

关键交互：

- 用户在首页只需要输入一句调研需求。
- 首页不展示快速/普通/专家模式，也不展示复杂分析模块配置。
- 点击提交后进入“调研范围确认页”，由下一页完成品类识别、竞品范围、分析维度、报告视角等配置。

跳转：

```text
工作台首页
  -> 点击开始调研
  -> 调研范围确认页
  -> 点击开始执行
  -> 调研执行页
```

#### 6.2.2 页面：调研范围确认页

用途：在正式执行前确认调研边界，避免 Agent 对产品品类、竞品范围和分析重点理解错误。

布局：

```text
左侧：全局导航
中间：调研范围确认表单
右侧：可选的任务摘要 / 后续执行预览
```

中间主区域分为三块：

1. Agent 识别结果确认
   - 展示用户原始需求。
   - 展示 Agent 识别出的产品 / 公司 / 研究对象。
   - 展示所属领域或品类。
   - 使用询问式文案，例如：“我们识别到你要调研的是 Trae，所属领域是 AI 原生 IDE / AI 代码编辑器，是否准确？”
   - 支持用户选择：准确继续、大致准确但补充、不准确我来说明。

2. 调研对象与维度配置
   - 候选竞品标签。
   - 支持多选、删除、手动新增竞品。
   - 分析维度标签，例如功能对比、定价策略、用户反馈、市场趋势、SWOT、技术能力、商业模式。
   - 支持手动新增分析维度。

3. 报告口径与补充要求
   - 报告视角：产品经理、运营、销售、投资人、通用综合。
   - 目标市场：中国大陆、全球、北美、东南亚、欧洲、不限。
   - 目标用户：个人用户、中小团队、大型企业、开发者、学生教育、不限。
   - 时间范围：近一月、近一年、不限。
   - 补充说明：特别关注点、必须纳入或排除的竞品、已有资料链接、输出偏好。

关键交互：

- 第一层由 Agent 根据用户输入预填，用户确认或修正。
- 第二层和第三层允许用户直接选择或补充。
- 点击“开始执行”后进入调研执行页。

说明：

- 当前阶段主要服务单用户学习和开发，不强求所有字段智能预填。
- 该页是 Agent Workflow 的前置 Human Gate，而不是传统问卷。
- 该页的确认结果会影响专家选择、数据采集对象、报告模块、写作口径和质检标准。

跳转：

```text
调研范围确认页
  -> 点击开始执行
  -> 调研执行页
```

#### 6.2.3 页面：调研执行页

用途：展示 Agent Workflow 的执行过程，让用户看到任务如何被拆解、专家如何工作、证据如何积累。

布局采用三栏：

```text
左侧：任务流水线
中间：实时协作思维流 / 专家动作流
右侧：实时证据库
```

左侧任务流水线：

- 需求理解。
- 编排派遣。
- 证据采集。
- 交叉分析。
- 质检审查。
- 报告撰写。
- 签发交付。

每个阶段展示：

- 阶段状态：等待中 / 进行中 / 完成 / 返工 / 失败。
- 负责专家。
- 阶段完成时间。

中间专家动作流：

- 展示每个专家的动作记录。
- 展示动作类型：发现、执行、分析、质检、撰写。
- 展示简短输出摘要。
- 支持点击某条动作展开详情。

右侧实时证据库：

- 展示采集到的证据卡片。
- 展示来源、可信度、摘要。
- 点击证据可打开原始 URL。
- 可按竞品、来源类型、可信度筛选。

关键交互：

- 用户可以观察执行进度，但 MVP 阶段不强制支持中途干预。
- 质检不通过时，页面展示 rework 原因和返工建议。
- 报告生成完成后，出现“查看报告”按钮。

跳转：

```text
调研执行页
  -> 查看报告
  -> 报告阅读页
```

### 6.3 一级菜单 2：我的调研

#### 6.3.1 页面：我的调研列表

用途：管理所有历史调研报告，是报告资产的入口。

布局：

```text
左侧：全局导航
中间：报告卡片网格
顶部：页面标题、搜索、筛选、新建调研按钮
```

报告卡片展示：

- 封面图或报告预览图。
- 报告标题。
- 竞品标签。
- 生成时间。
- 证据数。
- 结论数。
- 高置信结论数。
- 是否发生返工。
- 操作入口：报告、决策链路、图谱。

关键交互：

- 点击报告卡片主体进入报告阅读页。
- 点击“决策链路”进入该报告的 Trace 页面。
- 点击“图谱”进入知识图谱页。
- 点击“发起新调研”回到工作台新建调研。

跳转：

```text
我的调研
  -> 报告阅读页
  -> 决策链路页
  -> 知识图谱页
  -> 工作台首页
```

#### 6.3.2 页面：报告阅读页

用途：阅读最终报告，并在阅读过程中追溯证据、查看批注、进入决策链路或编辑模式。

布局采用三栏：

```text
左侧：报告目录 / 阅读进度
中间：报告正文
右侧：知识库 / 批注 / 证据库
```

顶部工具栏：

- 知识库：跳转或打开知识库相关内容。
- 决策链路：进入该报告的 Trace 页面。
- 编辑：进入报告编辑模式。
- 导出：导出报告或数据。

左侧报告目录：

- 展示章节标题。
- 展示阅读进度。
- 点击章节定位正文。

中间报告正文：

- 首屏展示报告元信息和关键统计。
- 展示质检摘要。
- 展示核心摘要和各模块分析。
- 正文中的引用以编号或标记展示。
- 点击引用后，右侧证据库定位到对应证据。

右侧栏：

- Tab 1：知识库 / 标注。
- Tab 2：批注。
- Tab 3：证据来源。

关键交互：

- 选中正文文字后出现浮层。
- 浮层支持标注：亮点、认同、存疑、待办。
- 浮层支持添加批注。
- 浮层支持加入知识库。
- 右侧批注列表点击后定位到正文原文。
- 右侧证据卡片点击后打开原始 URL。

#### 6.3.3 页面状态：报告编辑模式

报告编辑模式不是独立一级页面，而是报告阅读页的状态。

布局：

- 保持报告页三栏结构。
- 中间正文支持段落级编辑。
- 选中段落后进入编辑状态。
- 段落下方出现保存、取消按钮。

关键交互：

- 用户可新增、修改、删除段落文字。
- 保存后段落标记为 user-edited。
- 记录编辑前后内容。
- MVP 阶段不强制触发重新质检。

### 6.4 详情页面：决策链路

#### 6.4.1 页面：决策链路 / Agent Trace 回放

用途：查看某份报告从任务输入到报告生成的完整 Agent 执行过程。

布局：

```text
顶部：Trace 总览
中部：阶段筛选
主体：时间线步骤列表
展开区：单步 Prompt / Input / Output
```

顶部总览：

- 总 Token。
- 总耗时。
- 总步骤数。
- 参与专家数。
- 是否发生返工。

阶段筛选：

- 全部。
- 需求理解。
- 编排派遣。
- 证据采集。
- 交叉分析。
- 报告撰写。
- 质检审查。
- 签发交付。

步骤卡片：

- 步骤编号。
- 阶段标签。
- 专家头像 / 名称。
- 任务标题。
- 模型名称。
- Token 消耗。
- 耗时。
- 状态。

展开详情：

- Prompt。
- Input。
- Output。
- 关联证据。
- 关联报告章节。

关键交互：

- 点击阶段标签筛选步骤。
- 点击步骤卡片展开详情。
- 点击关联证据跳到报告证据栏或原始 URL。

## 7. 核心流程

### 7.1 主流程

```text
用户输入研究目标与竞品
  -> 系统理解任务
  -> 系统选择专家 Agent
  -> 资料采集专家采集证据
  -> 证据库生成并评分
  -> 分析专家生成结构化论点
  -> Evidence Reviewer 生成 Analysis Pack
  -> QA Gate 质检
  -> pass：进入报告生成
  -> rework：按建议返工，最多 1 次
  -> Report Writer 生成报告
  -> 用户阅读、标注、追溯、编辑、沉淀
```

### 7.2 专家 Agent 编排流程

```text
研究目标
  -> 任务路由
  -> 选择专家 Agent
  -> 分配阶段任务
  -> 并行或顺序执行
  -> 汇总输出
```

原则：

- 专家是可被主控 workflow 调度的任务型 Agent。Skill 是专家 Agent 可调用的方法、知识或工具规范，不再作为专家本体。
- 只读研究任务可并行。
- 依赖前序结论的任务顺序执行。
- 高风险工具调用不允许并行随意执行。

### 7.3 证据与结论流程

```text
网页 / 用户资料 / 搜索结果
  -> Evidence Item
  -> Evidence Scoring
  -> Claim Extraction
  -> Claim-Evidence Binding
  -> Analysis Pack
  -> Report Section
```

原则：

- 证据优先于结论。
- 结论必须能回溯证据。
- 低置信、冲突或缺证据的结论必须降级。

### 7.4 质检与返工流程

```text
Analysis Pack
  -> QA Scoring
  -> pass / rework
  -> rework 建议
  -> 最多返工 1 次
  -> 仍不通过：生成带风险提示报告或请求人工确认
```

### 7.5 报告阅读与沉淀流程

```text
报告阅读
  -> 查看证据引用
  -> 查看决策链路
  -> 标注 / 批注
  -> 加入知识库
  -> 可选生成 Research Memory 候选
```

## 9. 技术方案

### 9.1 总体架构

```text
Web Frontend
  -> API / Adapter Layer
  -> Evolva Agent Infra
  -> Local Storage / DB
  -> Evidence / Report / Trace / Memory
```

### 9.2 前端

建议采用：

- Next.js / React。
- Tailwind 或现有设计系统。
- React Query 管理请求状态。
- 图表使用 ECharts / Recharts。
- 图谱使用 React Flow / force graph。
- Markdown / rich text renderer 展示报告。

### 9.3 后端 / Adapter

两种可选方案：

1. 轻量本地 Web Adapter
   - Node API route 或 FastAPI。
   - 调用 Evolva CLI / Python API。
   - 读取 Evolva 生成的 trace、loop run、memory 文件。

2. 深度集成 Evolva
   - 直接在 Evolva 包内新增 Web API。
   - 暴露 workflow、trace、memory、skill、report 相关接口。

MVP 建议先用轻量 Adapter，降低改动 Evolva 底层的风险。

### 9.4 Evolva 能力复用

优先复用或参考：

- `EvolvaAgent`
- `WorkflowEngine`
- `LoopRunner`
- `TraceRecorder`
- `MemoryStore`
- `SkillStore`
- 内置 tools：web_search、web_fetch、read_file、file_to_text、remember、recall、save_skill

需要新增或包装：

- Parallel Expert Group。
- Expert Agent Library 配置。
- Evidence Library 数据结构。
- Analysis Pack 生成。
- QA Gate。
- Decision Trace Web 映射。
- Report Renderer。

### 9.5 数据存储

MVP 可选：

- 本地 JSON 文件。
- SQLite。

推荐使用 SQLite，便于结构化查询：

- reports
- expert_agents
- evidence_items
- claims
- analysis_packs
- qa_gate_results
- trace_steps
- annotations
- research_memories

### 9.6 Agent 执行策略

- 只读专家可并行。
- 报告生成前必须经过 QA Gate。
- 返工最多 1 次。
- 高风险工具默认不进入并行专家阶段。
- 数据获取不以绕过反爬为目标。
- 无法获取的数据必须标注缺口。

### 9.7 记忆系统策略

MVP 先实现 Research Memory 数据结构和基础写入规则，不强制接 mem0。

后续可采用混合架构：

- 业务数据库：证据、报告、claim-evidence、图表数据。
- Evolva Memory：治理型 lesson / research memory。
- Evolva Skill：专家 Agent 可调用的方法型知识、Prompt 片段和工具规范。
- mem0：用户长期偏好和跨会话个人记忆，可选。

## 10. 评估与验收

### 10.1 MVP 验收标准

- 能创建一条竞品研究任务。
- 能展示专家 Agent 编排结果。
- 能生成至少 20 条证据或 mock 证据。
- 证据有来源、摘要、可信度。
- 能生成 Analysis Pack。
- 能执行 QA Gate，并输出 pass / rework。
- 能生成最终报告。
- 报告中至少 3 条关键结论可追溯证据。
- 能查看决策链路 Trace。
- 能在我的调研中重新打开报告。

### 10.2 质量指标

- 证据覆盖率。
- 独立信源数量。
- 高置信证据占比。
- claim-evidence 绑定率。
- 质检通过率。
- 返工触发率。
- Trace 完整率。
- 报告引用可点击率。

### 10.3 用户体验指标

- 从创建任务到生成报告的总耗时。
- 用户能否看懂报告依据。
- 用户是否能定位某个结论的来源。
- 用户是否能通过决策链路定位错误阶段。
- 用户是否愿意标注或加入知识库。

## 11. 主要风险

### 11.1 数据源风险

风险：抖音、小红书、微博等平台无法稳定采集，容易造成“全网舆情”能力夸大。

应对：

- 不承诺绕过反爬。
- 使用公开网页、用户上传、搜索结果、第三方服务。
- 明确数据缺口。
- 将“全网舆情”改为“用户反馈 / 公开反馈”。

### 11.2 证据可信度风险

风险：置信度如果只靠 LLM 主观判断，会显得不专业，也容易误判。

应对：

- 使用多维度规则框架。
- LLM 只做摘要、解释和辅助判断。
- 低置信证据不得支撑强结论。
- 后续开发前细化评分规则。

### 11.3 图表幻觉风险

风险：雷达图、市场份额、波特五力等图表容易变成模型编造。

应对：

- 图表必须来自结构化数据。
- 每个图表都有数据表。
- 推断型数据必须标注。
- 支持查看来源和导出 CSV。

### 11.4 多 Agent 形式化风险

风险：专家库如果只是大量角色 Prompt，会变成概念堆叠。

应对：

- 专家定义为 Expert Agent，Skill 作为专家可调用能力。
- 每个专家有明确职责、工具范围和输出 Schema。
- 专家输出进入共享中间资产，而不是简单拼接。

### 11.5 质检失效风险

风险：质检员如果只是“再让模型看一遍”，价值有限。

应对：

- QA Gate 基于固定评分维度。
- 输出 pass / rework。
- 返工建议必须具体。
- 最多返工 1 次，避免死循环。

### 11.6 记忆污染风险

风险：错误、低置信、过期内容进入记忆后影响后续任务。

应对：

- 记忆有置信度、证据、状态和审计。
- 低置信进入 draft/quarantined。
- 写入 active memory 需要规则或人工确认。
- 后续开发前重点细化记忆系统决策。

### 11.7 工程范围风险

风险：Verda 功能很多，若全量复刻会导致项目失控。

应对：

- 分 P0/P1/P2。
- 先形态、再真实、再机制。
- P0 聚焦 Agent 核心链路。
- 高级图谱、情报中心、持续追踪后置。

## 12. 开发路线

### 12.1 Phase 0：产品与数据结构确认

- 确认 P0 范围。
- 细化专家 Agent Schema。
- 细化证据置信度规则。
- 细化 QA Gate 评分规则。
- 细化 TraceStep 映射。
- 细化 Research Memory 写入/召回规则。

### 12.2 Phase 1：Mock 形态复刻

- 搭建 Web 基础页面。
- 使用 mock 数据复刻报告、证据库、决策链路、我的调研。
- 跑通主要交互。

### 12.3 Phase 2：接入真实 Workflow

- 接入 Evolva 或 Adapter。
- 跑通专家 Agent 编排。
- 生成真实或半真实 Trace。
- 让证据库、Analysis Pack、QA Gate 进入真实数据流。

### 12.4 Phase 3：核心机制增强

- 并行专家组。
- 图表数据表。
- 标注与知识库。
- 最小知识图谱。
- Research Memory 初版。

### 12.5 Phase 4：复盘与优化

- 对一次完整竞品调研做端到端演示。
- 记录 bad cases。
- 调整评分规则、专家 Prompt、QA Gate、报告结构。
